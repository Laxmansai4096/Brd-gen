16. Scale Drivers

Use the following generic drivers.

Driver	Baseline	Elasticity
Use cases	1	0.70
Integrations	2	0.65
Data sources	2	0.60
Personas	2	0.45
Channels	1	0.60
Environments	3	0.40
Languages	1	0.50
Components	6	0.55
Documents	50,000	0.30

Scale factor floor:

0.50

Formula:

$$ ScaleFactor = MAX(Floor,\;1 + Elasticity \times (\frac{Current}{Baseline}-1)) $$

Example:

Baseline personas = 2
Current personas = 4
Elasticity = 0.45

$$ 1+0.45(4/2-1) $$ $$ =1+0.45 $$ $$ =1.45 $$

25. Task Effort Formula

A robust base formula is:

$$ E_{task} = BaseDays \times PhaseRigour \times ScaleFactor \times ComplexityFactor \times ComplianceFactor \times SecurityFactor \times OtherApplicableFactors $$

But only applicable factors are applied.

For example:

Task:
API integration

Base = 6 days
Phase = 0.75
Integration scale = 1.30
Complexity = 1.25
Compliance = 1.00
Security = 1.10
$$ 6 \times .75 \times 1.30 \times 1.25 \times 1.10 $$

= calculated deterministic effort.

32. Schedule Formula

For a task requiring \(E\) person-days and assigned capacity \(C_d\) per day:

$$ Duration = \min d $$

such that:

$$ \sum_{i=1}^{d} Capacity_i \ge E $$

while respecting:

dependencies
holidays
leave
working hours
resource capacity
max FTE
ramp rate
phase overlap.
33. Parallelism

If a task requires 20 person-days:

With 1 FTE:

$$ 20 / 1 = 20 days $$

With 2 FTE:

$$ 20 / 2 = 10 days $$

But the scheduler must not assume infinite parallelism.

Use:

max FTE per role
max ramp per week
min FTE granularity
task dependencies
phase overlap
34. Feasibility Rules

Master configuration:

Max FTE per role = 20
Max team ramp/week = 80
Phase overlap fraction = 0.50
Minimum FTE granularity = 0.25

Example:

Required AI engineers:

6.25 FTE

Available maximum:

4 FTE

The engine must not silently reduce the estimate.

Instead:

FEASIBILITY WARNING

Required peak FTE: 6.25
Available: 4.00

Result:
Schedule must be extended.
35. Ramp Constraint

If:

Previous week = 2 people
Maximum ramp = 3 people/week
Required = 7 people

Allowed next week:

$$ 2 + 3 = 5 $$

Therefore 7 cannot be loaded immediately.

The scheduler spreads the work.

36. Phase Overlap

If:

Phase duration = 10 weeks
Overlap fraction = 0.50

The next phase may start after approximately:

$$ 10 \times (1-.50)=5 $$

weeks of elapsed phase time, subject to dependency rules.

This should be a configurable scheduling rule, not an arbitrary LLM decision.

37. Reference Duration

Reference duration is not the final schedule.

Example:

Reference duration = 30 working days

The scheduler attempts to fit work into that window.

If capacity is insufficient:

Reference duration = 30
Calculated feasible duration = 38

Then:

Schedule = 38 working days

and report:

+8 days due to capacity constraint
38. Cost Engine

Labor cost:

$$ LaborCost_r = Hours_r \times Rate_r $$

or, if using person-days:

$$ LaborCost_r = PersonDays_r \times DayRate_r $$

Total labor:

$$ TotalLabor = \sum_r LaborCost_r $$

Additional costs:

$$ TotalCost = Labor + Cloud + Licenses + Tools + Infrastructure + Travel + OtherApprovedCosts $$
39. PM / Governance Overhead

Current configuration:

PM/governance overhead = 12%

This must have clear semantics.

If applied as an explicit overhead:

$$ GovernanceCost = BaseDeliveryCost \times 12\% $$

However, because PM is already a role in the task library, the accelerator must avoid double counting.

Recommended rule:

Choose one authoritative PM mechanism per calculation version.

Either:

PM task effort

or:

PM/governance percentage

but do not silently apply both.

40. Leave and Buffer

Current workbook configuration:

Leave + buffer = 0%
Contingency = 10%

Separate these concepts.

Recommended:

$$ PlanningEffort = BaseEffort + LeaveBuffer $$

Then:

$$ ContingencyEffort = PlanningEffort \times Contingency\% $$

and:

$$ FinalEstimate = PlanningEffort + ContingencyEffort $$

The exact application should be configurable.

41. Transition Estimation

For transition tiers:

Existing solution
        +
Target tier requirements
        ↓
Gap analysis
        ↓
Reusable capability
        ↓
Transition work
        ↓
Rework uplift
        ↓
Mobilisation floor

Rework uplift:

1.15

Mobilisation floor:

0.05

Formula concept:

$$ TransitionEffort = GapEffort \times ReworkUplift $$

Then:

$$ FinalTransitionEffort = MAX(TransitionEffort,\ MobilisationFloor) $$

The exact unit for the 0.05 floor must be explicitly configured — e.g. percentage of a defined target effort or normalized base — rather than hard-coded ambiguously.

44. RAG Sizing

Vector count:

$$ VectorCount = Documents \times ChunksPerDocument $$

Storage approximation:

$$ EmbeddingStorage = VectorCount \times Dimensions \times BytesPerDimension $$

plus index/storage overhead.

Retrieved context:

$$ RetrievedTokens = TopK \times TokensPerChunk $$

Total model input:

$$ InputTokens = PromptTokens + RetrievedTokens $$

LLM consumption:

$$ TotalTokens = InputTokens + CompletionTokens $$

These values feed:

capacity
model usage
cloud cost
performance
architecture

not generic development effort.

63. The final product definition

The accelerator is essentially five systems combined:

┌──────────────────────────────────────────┐
│ 1. REQUIREMENTS INTELLIGENCE             │
│    Understand → Clarify → Resolve        │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ 2. SOLUTION INTELLIGENCE                 │
│    Capability → Solution → Architecture  │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ 3. DELIVERY ESTIMATION ENGINE            │
│    WBS → Effort → Resources → Schedule   │
│    → Cost → Feasibility                  │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ 4. GOVERNANCE / HITL                     │
│    Review → Change → Impact → Approve    │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ 5. BRD DOCUMENT ENGINE                   │
│    Canonical model → DOCX/PDF/PPTX       │
└──────────────────────────────────────────┘

The most important architectural principle is:

The accelerator does not generate a BRD first and then estimate the project. It builds an approved, structured project model first; the BRD, WBS, estimate, schedule, cost, architecture and presentations are different views of that same model.

That makes the solution reusable across clients, industries, technologies and delivery tiers, while the reference project is simply one regression/golden test case for proving that the generic accelerator can reproduce the required level of BRD detail.
